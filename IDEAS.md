# BasedCode ideas

Aim: make BasedCode the place where users can trust agents with bigger jobs. AI reduces implementation effort, but maintenance, architectural complexity and verification still matter.

| # | Idea | Scope | Proposed behavior | Value and considerations |
| --- | --- | --- | --- | --- |
| 1 | Isolated task workspaces | Practical improvement | Give substantial tasks their own Git worktree, dev server and allowed resources. Deliver a diff, check results and preview; integrate accepted changes with conflict resolution. | Foundation for parallel agents, unattended work and competing solutions. **Starting priority.** |
| 2 | “Prove it” completion screen | Practical improvement | Link each requirement to implementation and verification. Record check commands, exit status and revision; include UI screenshots and explicitly mark unverified behavior. Invalidate evidence after relevant edits. | Makes completion claims inspectable and prevents stale green badges. **Starting priority.** |
| 3 | Bounded authorization | Practical improvement | Authorize outcomes with limits, such as permitted paths, project scripts, network access and stopping before commits. Explain affected resources and reversibility at approval time; enforce limits through process isolation. | Supports longer autonomous runs with meaningful boundaries. **Starting priority.** |
| 4 | Editing and review surface | Practical improvement | Add file editing, inline diff comments and questions about selected code. Support focused agent revisions that preserve manual edits and anchor comments to the reviewed hunk version. | Keeps review, explanation and correction in one workflow. |
| 5 | Recovery with explicit limits | Practical improvement | Extend checkpoints into a timeline of file edits, Git state, commands, processes and known external effects. Preview restoration; support explicit database and service snapshot adapters. | Makes recovery predictable and identifies effects requiring manual intervention. |
| 6 | Executable task board | Larger-task feature | Represent plans as dependent tasks with acceptance criteria and review states. Pause, retry or redirect individual tasks; retain artifacts, verification and useful discoveries from failed attempts. | Makes multi-day work less dependent on one long conversation. |
| 7 | Project knowledge with sources | Larger-task feature | Maintain architecture, commands, invariants and decisions with links to code or recorded human decisions. Flag changed sources and contradictory claims for revalidation. | Provides durable context without silently accumulating stale assumptions. |
| 8 | Agent failure flight recorder | Larger-task feature | Show provider failures, fallbacks, context changes, repeated edits, approvals and check results in a causal timeline. Export reproducible diagnostic bundles with sensitive content excluded by default. | Makes stalled runs and BasedCode bugs easier to diagnose. |
| 9 | Repository-specific model routing | Larger-task feature | Measure success, corrections, latency and cost by task type. Compare models in isolated environments with identical starting conditions and acceptance checks. | Optimize for the cheapest successful result using observed project performance. |
| 10 | Competing implementation tournament | Moonshot | Run multiple isolated implementations of one specification, exploring minimal changes, performance or alternative designs. Apply identical checks and present tradeoffs with a review recommendation. | Explores alternatives while preserving evidence; avoid automatically combining incompatible patches. |
| 11 | Reproducible development time machine | Moonshot | Capture runtimes, dependencies, configuration references, fixtures and service snapshots so an old task can reopen in its original environment. Switch between failing and fixed versions. | Makes historical bugs and fixes reproducible. |
| 12 | Bug-to-regression-test pipeline | Moonshot | Turn browser recordings, stack traces or incident logs into a reproduction, minimized case, regression test, proposed fix and verified result. Keep each stage inspectable. | A reliable reproduction alone can save substantial debugging time. |
| 13 | Architecture simulator | Moonshot | Forecast affected callers, schemas, tests and repositories before interface changes. Rehearse migrations in disposable environments and measure consequences across connected services. | Gives evidence for contract changes and large migrations. |
| 14 | Asynchronous engineering inbox | Moonshot | Run batches of bounded jobs and collect reviewable results, blocked decisions and failed experiments. Group related questions and highlight consequential decisions. | Lets users supervise unattended work with less interruption. |

Suggested starting sequence: isolated task workspaces → completion evidence → bounded authorization. Together they provide the foundation for longer autonomous work and many of the larger ideas above.
